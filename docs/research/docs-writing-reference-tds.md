# 문서 작성 참고: TDS Mobile

Tide Storybook 문서가 장황하다는 피드백에 따라, 짧고 요지가 분명한 문서 사례로 TDS Mobile 문서를 살펴봤다. 디자인과 브랜드는 참고하지 않고 **작성 패턴**만 본다.

조회일: 2026-11-10

## 출처

- [Button](https://tossmini-docs.toss.im/tds-mobile/components/button/)
- [Badge](https://tossmini-docs.toss.im/tds-mobile/components/badge/)
- [Loader](https://tossmini-docs.toss.im/tds-mobile/components/loader/)
- [Colors](https://tossmini-docs.toss.im/tds-mobile/foundation/colors/) (Foundation)
- [시작하기](https://tossmini-docs.toss.im/tds-mobile/start/)

본문 글자 수(코드 포함, HTML 태그 제외 대략): Button 약 6,000자, Badge 약 2,000자, Loader 약 1,500자, 시작하기 약 830자, Colors 약 3,200자(대부분 색 이름과 hex).

## 관찰한 사실

### 페이지 구조

- Component 페이지 순서는 `제목 → 한두 문장 요약 → 기본 미리보기 → 사용 예제(또는 사용법) → 접근성 → 인터페이스`다. Badge, Loader에는 접근성 절이 없다.
- 사용 예제의 소제목은 **할 일**로 짓는다: 「크기 조정하기」, 「타입 설정하기」, 「레이블 추가하기」. 상태 이름일 때는 명사 하나로 짓는다: 「로딩」, 「비활성화」.
- 시작하기는 번호 붙은 3단계(`1. 필수 패키지 설치하기 → 2. Provider 설정하기 → 3. 사용하기`)뿐이다. 단계마다 한두 문장과 코드 한 덩어리가 있다.
- Foundation(Colors)은 `요약 2문장 → 기본 사용법(설치 1줄, 코드 1개) → 값 목록`이다. 설계 배경이나 규칙 설명이 없다.

### 첫 문단

- 첫 문장은 「X 컴포넌트는 ~할 때 사용해요」 형식이다. **무엇이고 언제 쓰는지**를 한 문장에 담는다.
- 둘째 문장이 있으면 쓰임새를 예로 든다(Button: 폼 제출, 다이얼로그 열기 등). 셋째 문장은 없다.
- Badge는 한 문장(「항목의 상태를 빠르게 인식할 수 있도록 강조하는 데 사용돼요」)이다.

### 예시와 설명의 비율

- 소제목 하나에 **설명 1~2문장 + 예시 1개**가 기본이다. 설명 문장은 대개 「`size` 속성을 사용하세요. small, medium, large 중 하나를 선택할 수 있어요」처럼 **prop 이름 + 고를 수 있는 값**이다.
- 값마다 의미가 다르면 하위 소제목(`#### fill`, `#### weak`)이나 짧은 목록(`inline: 다른 요소와 나란히 배치돼요`)으로 나눈다.
- 예시 코드가 설명보다 길다. 설명이 예시보다 길어지는 곳은 「색상 업데이트」(CSS 변수 목록)뿐이다.

### 문장

- 해요체(「사용해요」, 「선택할 수 있어요」)로 쓴다.
- 한 문장에 한 가지를 말한다. 「왜 이렇게 만들었는지」는 거의 없고, 있으면 사용자 이득으로 쓴다(「버튼의 너비는 변하지 않아요」).
- 구현 방식, 테스트, 내부 결정은 문서에 없다.

### 표·코드·Do/Don't

- 접근성은 표(`속성 | 접근성 효과 | 설명`)로 기본 제공 동작을 보여 주고, 「추가로 지원해야 하는 접근성」 절에서 개발자가 할 일을 상황별 소제목(「아이콘만 있거나 설명이 부족할 때」) + 코드로 보여 준다.
- 인터페이스는 `속성 | 기본값 | 타입` 표 하나이고, 설명은 타입 아래 한 문장이다. 필수 prop은 이름 뒤 `*`로 표시한다.
- 별도의 Do/Don't 절은 보지 못했다. 주의할 점은 접근성 절의 상황별 안내로 들어간다.
- 시작하기의 설치 명령은 패키지 매니저 탭(npm/pnpm/yarn/bun)으로 보여 준다.

## Tide에 가져올 점

1. **첫 줄 한 문장 요약.** 「무엇이고 언제 쓰는지」를 한 문장으로 쓰고, 나머지 특징은 본문의 해당 절로 보낸다.
2. **할 일로 짓는 소제목 + 1~2문장 + 예시 1개.** 설명은 prop 이름과 값부터 말한다.
3. **문서에는 사용자가 할 일과 결과만.** 구현 방식, CI·테스트, 결정 과정은 티켓·ADR에 두고 문서에는 필요할 때 링크만 둔다.
4. **접근성은 「기본으로 되는 것」과 「앱이 할 일」로 나눈다.**
5. **Props는 표 하나로.** Tide는 `ArgTypes` 블록이 이미 표를 그리므로, 표와 겹치는 문장 목록을 두지 않는다.

## 가져오지 않을 점

- **해요체.** Tide 문서는 지금까지 합니다체로 썼다. 말투를 바꾸려면 모든 페이지를 다시 써야 하므로 이번 기준에서는 합니다체를 유지한다(사용자 결정이 필요한 선택지로 남긴다).
- **Do/Don't 생략.** Tide는 Do/Don't를 story로 보여 주는 관례(티켓 09)가 있고, 잘못 쓰기 쉬운 접근성 실수를 보여 주는 데 쓸모가 있어 유지한다.
- **「쓰지 않을 때」 생략.** TDS에는 없지만 Tide는 비슷한 Component(Progress, Skeleton) 사이의 선택을 돕는 데 필요해 유지한다. 대신 짧게 쓴다.
- **값 목록만 있는 Foundation.** Tide의 Foundation은 Semantic Token 사용 규칙(강도 생략 금지 등)이 있어 규칙 절이 필요하다. 다만 규칙은 목록으로 짧게 쓴다.
- **디자인, 브랜드, 색, 컴포넌트 이름.** 작성 패턴만 참고한다.
