# 문서 작성 기준

Storybook 문서(`apps/docs/src/**/*.mdx`)를 쓸 때 지킬 기준이다. 참고 사례는 [TDS Mobile 문서 리서치](../research/docs-writing-reference-tds.md)에 있다.

## 핵심 규칙

1. **첫 줄은 한 문장 요약이다.** 「무엇이고 언제 쓰는지」만 쓴다. 특징(기본 이름, 색, 서버 컴포넌트 여부 등)은 해당 절로 보낸다.
2. **한 문단에 요지 하나, 한 문장에 사실 하나.** 문단은 3문장을 넘기지 않는다. 문장은 60자 안팎에서 끊는다.
3. **할 일과 결과만 쓴다.** 구현 방식, 테스트·CI, 결정 과정은 티켓·ADR에 둔다. 사용자가 알아야 하는 근거만 한 구절로 남기고, 더 필요하면 링크를 단다.
4. **설명보다 예시가 먼저 눈에 들어오게 한다.** 소제목 하나에 설명 1~2문장과 예시 하나.
5. **말투는 합니다체.** 「~합니다」, 「~씁니다」. 명령보다 사실로 쓴다(「`size`로 크기를 고릅니다」).

## 페이지 유형별 템플릿

### Component

```
# 이름
한 문장 요약.
<Canvas 기본 예시>

## 사용 시점 / 쓰지 않을 때   ← 목록 2~3개씩. 대안 Component 이름을 적는다.
## 예시                       ← 소제목은 할 일(「크기 바꾸기」). 1~2문장 + Canvas.
## Do/Don't                   ← 잘못 쓰기 쉬운 것만. 소제목이 곧 규칙이다.
## 접근성                     ← 「기본 제공」과 「앱이 할 일」로 나눈다.
## Props                      ← ArgTypes 표. 표에 없는 사실(받는 HTML 속성, ref, className 병합)만 한두 문장.
```

### Foundation

```
# 이름
한 문장 요약.
## 쓰는 법     ← 가장 흔한 class·변수 하나를 코드로.
## 규칙        ← 목록. 한 항목에 규칙 하나.
## 값          ← Canvas나 표. 읽는 법(L, D 같은 약어)만 한 문장.
```

### 시작하기

```
# 이름
한 문장 요약(무엇을 하고 나면 무엇을 쓸 수 있는지).
## 준비
## 1. 단계 / 2. 단계 …   ← 단계마다 1~2문장 + 코드 하나.
## 상황별 안내            ← 「~할 때」 소제목. 필요한 경우에만.
## 다음 단계
```

## 표·코드

- 코드는 복사해서 바로 쓸 수 있게 쓰고, 첫 줄에 파일 경로 주석을 단다(`// app/layout.tsx`).
- 비교할 축이 둘 이상이면 표를 쓴다. 목록 항목이 「이름: 설명」 모양으로 4개를 넘으면 표를 고려한다.
- **주의**: 지금 Storybook 설정에는 `remark-gfm`이 없어 MDX 안의 Markdown 표가 표로 그려지지 않는다(Storybook 10.6.6 문서 「remarkPlugins」, 빌드 결과에서 확인). 고치기 전까지 MDX에서는 표 대신 목록을 쓴다.
- Props는 `ArgTypes` 블록이 그린다. 같은 내용을 문장 목록으로 되풀이하지 않는다. 설명이 부족하면 Component 소스의 JSDoc을 고친다.

## Do/Don't

- Do: 「`size`는 `xs`~`lg`이고 기본값은 `md`입니다.」
- Don't: 「`size`는 같은 size Component의 텍스트 옆 아이콘 크기와 같으며, 이는 spec의 아이콘 크기 규칙을 따른 것으로 …」
- Do: 「대비는 light·dark 모두 자동으로 검사합니다.」
- Don't: 「Semantic Token을 더하면서 대비 쌍이나 제외 사유를 등록하지 않으면 CI가 실패합니다.」(기여자용 정보. 티켓·ADR에 둔다.)

## 범위

- 이 기준은 Storybook MDX 페이지에 적용한다.
- `docs/principles/`, `docs/standards/`의 원문은 Storybook이 그대로 불러와 보여 주지만, 저장소 문서이기도 해서 이 기준을 아직 적용하지 않았다.
