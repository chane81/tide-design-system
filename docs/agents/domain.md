# 도메인 문서

엔지니어링 스킬이 코드베이스를 탐색할 때 이 저장소의 도메인 문서를 어떻게 활용하는지 정리한다.

## 탐색 전에 읽을 것

- 루트의 **`GLOSSARY.md`**
- **`docs/decisions/`**: 작업할 영역과 관련된 ADR을 읽는다. 이 저장소는 ADR을 `docs/adr/`가 아니라 `docs/decisions/`에 둔다.
- **`docs/research/`**: 결정의 근거가 된 리서치 문서

이 파일들이 아직 없으면 **그냥 넘어간다**. 없다고 알리지 말고, 미리 만들자고 제안하지도 않는다. `/domain-modeling` 스킬이 용어나 결정이 실제로 확정될 때 필요한 만큼 만든다.

## 파일 구조 (single-context)

```
/
├── GLOSSARY.md
├── CLAUDE.md
└── docs/
    ├── agents/          ← 스킬 설정 (이 파일 포함)
    ├── decisions/       ← ADR (0001-*.md, 0002-*.md ...)
    ├── research/        ← 리서치 결과 (출처 인용)
    ├── progress/        ← wayfinder 지도, 스펙, 티켓 (이슈 트래커)
    ├── principles/      ← 산출물: 디자인 원칙
    ├── standards/       ← 산출물: 측정 가능한 기준 (접근성, 문서 작성 등)
    ├── foundations/     ← 산출물: 컬러, 타이포, 간격 등 파운데이션
    └── components/      ← 산출물: 컴포넌트 문서
```

## Storybook 문서는 작성 기준을 따른다

`apps/docs/src/**/*.mdx`와 Storybook이 불러오는 원문을 쓰거나 고칠 때는 [문서 작성 기준](../standards/docs-writing.md)을 따른다.

## ADR에는 근거 원칙을 적는다

모든 ADR은 본문 위쪽에 `근거 원칙: ①` 형태로 `docs/principles/README.md`의 원칙 번호를 적는다. 그리고 원칙 문서의 "원칙에서 나온 결정" 목록에 그 ADR 링크를 추가한다.

## 용어집의 어휘를 쓴다

결과물(이슈 제목, 리팩터링 제안, 가설, 테스트 이름 등)에서 도메인 개념을 가리킬 때는 `GLOSSARY.md`에 정의된 용어를 쓴다. 용어집이 피하라고 명시한 동의어로 바꿔 쓰지 않는다.

필요한 개념이 용어집에 없다면 둘 중 하나다. 프로젝트에서 쓰지 않는 말을 새로 만들고 있는 것이거나(다시 생각해 본다), 용어집에 실제로 빠진 것이다(`/domain-modeling`용으로 기록해 둔다).

## ADR과 충돌하면 드러낸다

결과물이 기존 ADR과 맞지 않으면 조용히 덮어쓰지 말고 명시한다.
